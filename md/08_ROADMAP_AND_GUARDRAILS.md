# 08. 개발 로드맵 · 기존 기능 보존 원칙 · 향후 확장

## 합의된 순서

1. 메인 홈의 반응형 대시보드 최적화.
2. 01 라인 기본정보의 필터/KPI/그래프/RAW/Excel/버전 기능 안정화.
3. 02~16 업무 화면을 각각 실무 데이터 정의와 승인 기준을 받은 후 순차 제작.
4. 전체 데이터·메뉴 연결, 변경 이력·보고·자동 검증 고도화.
5. **가장 마지막**: 회사 GitHub Enterprise 팀별 조회·수정·검토·관리자 권한/SSO/승인.

단 보안 검토는 마지막에 하더라도 **실데이터 공개 금지·인증 비밀 코드 기록 금지**는 처음부터 적용.

## 01 확정 화면/기능 보존

- KPI 5개 / 그래프 3개 / Raw Data 46열.
- 한 화면 맞춤, 확대 시 콘텐츠 자체 재배치.
- **최소화 삭제**: 최대화 ↔ 원래대로만.
- 가로/세로 스크롤 중 고정행과 고정열이 서로 겹치지 않게.
- 왼쪽 6그룹 16메뉴는 홈과 01이 동일; `nav.js`/`nav.css` 한 곳에서만 변경.
- 기존 원본 `.xlsx` 열 순서, 데이터 버전·파일보존 원칙.

## 미래 02~16 화면을 만들 때

- 업무 목적, 사용자, RAW 원천, 산출물/승인 여부, KPI, 그래프, 표, 수정/변경이력의 8가지 요소 먼저 확인.
- 일단 공통 레이아웃과 nav를 연결하되 새로운 기능이 기존 01/홈을 망가뜨리지 않도록 한 화면씩 출시.
- '07 설비 제원정보'는 **전력·냉각수·가스·CDA·배기·발열/냉각능력·배관/덕트**를 통합해서 다룸.
- 도면/Utility/반입/안전 협의는 실제 승인 기준과 데이터 출처 확인 후 자동 판단.
- 시스템 전체의 9개 상위 교육/전문가 메뉴 기획과 기존 운영 16개 도메인은 별도의 정보구조 후보; 승인 없이 둘을 섞거나 하나를 제거하지 말 것.

## 개발 협업 스타일

- 코딩 초보 사용자에게 개발 세부 명령을 무작정 요청하지 말고, 우선 **완성된 전체 ZIP 프로젝트**를 제공.
- ZIP명 `EDS_LinePlanning_YYYY-MM-DD_vX.Y.zip`. 프로젝트 디렉터리 구조와 README 동봉.
- GitHub Desktop 설치를 강요하지 말 것. GitHub 웹 업로드 방법을 우선 설명.
- 이전의 승인된 UI 디자인·버튼·데이터 필드를 변경했다면 먼저 사용자에게 알려야 함.
- 이미지 시안은 화면 기능의 증거가 아님. 실제 브라우저 검증으로만 기능 완료 표현.
- 원격 저장소 자료를 받지 않고 기존 사용자 데이터를 임의로 만들어 넣지 말 것.
